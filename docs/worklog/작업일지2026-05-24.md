## 5. 중요한 결정
- 결정: 홈 전체 페이지를 한 번에 만드는 Stitch 전략 대신 섹션 단위 생성 전략으로 전환한다.
- 이유: 전체 페이지 생성은 품질 편차가 크고 빈 결과나 비주얼 자산 드리프트가 반복됐다.
- 대안: 홈 전체를 계속 프롬프트 강화로 밀기
- 왜 대안을 버렸는지: 생성 비용과 시간 대비 품질 회복이 불안정했다.

- 결정: Figma는 Stitch 결과를 정리하는 프레임 조립 단계에서 사용한다.
- 이유: Stitch는 초안 생성에 강하고, Figma는 구조 정리와 프레임 통합에 적합하다.
- 대안: 처음부터 Figma를 선행 설계 도구로 사용
- 왜 대안을 버렸는지: 현재 워크플로우와 사용자의 의도는 `stitch -> figma` 순서에 맞다.

- 결정: 도구 설치/인증/복구 절차를 스킬로 캡슐화한다.
- 이유: Stitch와 Figma 모두 한 번의 설치로 끝나지 않았고, 인증/연결/트러블슈팅을 매번 다시 설명하는 비용이 컸다.
- 대안: 메모와 작업일지에만 기록
- 왜 대안을 버렸는지: 실행 가능한 자동화가 없으면 다음 세션에서도 다시 수동 복구를 반복할 가능성이 높다.

## 6. 잘못 생각했던 점 / 수정된 이해
- 처음에 잘못 생각한 점: Stitch는 API key만 있으면 바로 생성까지 될 것이라고 봤다.
- 왜 그 생각이 틀렸는지: 실제로는 API key는 도구 목록 조회 수준이고, 생성 계열은 OAuth access token과 quota project가 필요했다.
- 실제 원인: 인증 모델이 다르고, SDK 내부에서 API key가 OAuth보다 우선돼 경로가 꼬였다.
- 다음부터의 판단 기준: Stitch 생성 실패 시 먼저 인증 방식과 quota project를 분리해 확인한다.

- 처음에 잘못 생각한 점: Figma는 Desktop 앱 설치와 플러그인 설치까지만 하면 바로 도구가 보일 것이라고 봤다.
- 왜 그 생각이 틀렸는지: 실제 병목은 앱 커넥터 접근 권한과 세션 도구 인덱싱이었다.
- 실제 원인: 플러그인 매니페스트는 커넥터 의존성만 선언하고 있었고, 커넥터가 `isAccessible: false`이면 도구가 0개였다.
- 다음부터의 판단 기준: Figma는 설치 여부보다 커넥터 접근 상태와 새 세션에서의 `_whoami` 성공 여부를 본다.

- 처음에 잘못 생각한 점: MCP startup timeout을 임의 설정으로 늘리면 해결될 수 있다고 봤다.
- 왜 그 생각이 틀렸는지: 현재 Codex 버전에서 transport 없는 `mcp_servers.codex_apps` 블록은 invalid config였다.
- 실제 원인: 버전에 맞지 않는 설정 형식
- 다음부터의 판단 기준: Codex 설정 우회는 현재 버전 형식을 먼저 확인한 뒤에만 적용한다.

## 7. 발생한 이슈 / 오류

### 이슈 1
- 증상: Stitch는 연결되지만 실제 홈페이지 생성이 실패하거나 인증 오류가 났다.
- 오류 메시지: OAuth access token 요구, project/quota 관련 실패
- 영향 범위: Stitch 생성 전부 불가
- 처음 의심한 원인: API key 누락 또는 SDK 사용법 문제
- 실제 원인: API key만으로는 생성이 안 되고 OAuth + quota project가 필요했다

### 이슈 2
- 증상: 홈 전체 페이지 생성 결과가 빈 화면, 부분 화면, 비주얼 카드 드리프트로 흔들렸다.
- 오류 메시지: 명시적 런타임 오류보다는 결과 품질 문제
- 영향 범위: 홈 초안 품질 저하
- 처음 의심한 원인: 프롬프트가 조금 약한 정도
- 실제 원인: Stitch가 긴 전체 페이지 요구를 안정적으로 유지하지 못하는 생성 패턴

### 이슈 3
- 증상: Figma 플러그인을 설치했는데도 `use_figma`, `create_new_file`이 보이지 않았다.

- 영향 범위: Figma 조립 작업 불가
- 처음 의심한 원인: 플러그인 설치 실패
- 실제 원인: 커넥터 접근 상태 `isAccessible: false`, 그리고 세션 재시작 전 도구 인덱스 미반영

## 8. 해결 접근
1. Stitch는 기본 smoke test로 연결성을 먼저 확인했다.
2. 생성 실패 후 인증 레이어를 분리해 보며 `gcloud` ADC와 quota project를 복구했다.
3. 홈 전체 생성 품질 문제는 프롬프트 강화만으로 해결하려 하지 않고, 결과물을 비교한 뒤 섹션 분리 생성으로 전략을 바꿨다.
4. Figma는 플러그인 캐시, 매니페스트, 커넥터 캐시를 차례로 확인해 실제 병목이 커넥터 접근이라는 점을 좁혔다.
5. 커넥터 재연결 후에는 반드시 새 세션에서 다시 확인했고, 최종 검증은 `_whoami` 성공으로 했다.
6. 재발 방지를 위해 Stitch와 Figma 모두 설치/인증/검증 절차를 스킬과 트러블슈팅 문서로 남겼다.

### 13.1 retain 가치가 높은 사실
- Stitch 생성은 API key만으로 충분하지 않고 OAuth access token과 quota project가 필요했다.
- 이 환경에서 Stitch 관련 quota project는 `cbk-02`다.
- Stitch 전체 페이지 생성보다 섹션 단위 생성이 훨씬 안정적이었다.
- 현재 홈 기준 최우수 Stitch 섹션은 `home-demo-v2`다.
- Figma는 플러그인 설치만이 아니라 커넥터 접근과 새 세션 인덱싱이 필요했다.
- Figma 도구 생존 여부는 `_whoami` 성공으로 판단하는 것이 가장 확실하다.
- `stitch-setup`, `figma-setup` 스킬을 만들어 다음 세션 복구 비용을 크게 줄였다.

### 13.3 reflect에 유용한 교훈 후보
- 생성형 UI 도구가 긴 페이지 요구를 흔들기 시작하면 프롬프트를 더 키우기보다 섹션 분해 전략으로 바꾸는 편이 낫다.
- 설치 완료와 사용 가능은 다르다. 플러그인형 도구는 실제 callable probe가 있어야 한다.
- 설정 우회는 빠른 해결처럼 보여도 런타임 형식과 맞지 않으면 전체 작업 환경을 깨뜨릴 수 있다.

## 14. 에이전트 협업 메모
- 오늘도 코딩/검증 위임보다 감독관이 직접 도구 체인을 정비하는 비중이 컸다.
- Design 역할은 실제로 `gemini`보다 `stitch + figma + 감독관 판단` 쪽이 더 핵심적이었다.
- 구현 단계로 넘어가면 Agent K는 STT-TTS 데모와 페이지 구현을 TDD로 쪼개야 하고, Agent C는 Playwright 사용자 여정을 조기에 정의하는 것이 유리하다.

## 15. 사람이 나중에 봤을 때 유용한 한 문단 회고
오늘은 화면을 만드는 날이면서 동시에 도구를 믿을 수 있게 만드는 날이었다. Stitch와 Figma 모두 “설치됐다”는 상태와 “실제로 지금 쓸 수 있다”는 상태 사이에 큰 차이가 있었고, 그 틈을 하나씩 메우면서 인증, 커넥터, 세션, 생성 품질 문제를 정리했다. 결과적으로 홈 페이지는 전체 페이지 생성보다 섹션 분리 생성이 맞다는 판단을 얻었고, 이걸 Figma에서 묶는 기준까지 문서화했다. 내일부터는 더 이상 설치/복구가 아니라 실제 Figma 조립과 하위 페이지 확장에 집중할 수 있는 상태가 됐다.
