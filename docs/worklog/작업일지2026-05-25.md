## 5. 중요한 결정
- 결정: 홈 음성 데모 v1은 backend 없이 `SpeechRecognition + speechSynthesis + canned reply` 조합으로 구현한다.
- 이유: 사용자가 요구한 마이크 권한, transcript, state change, TTS 응답을 가장 빠르게 검증 가능한 범위에서 만족할 수 있다.
- 대안: 실제 STT/TTS 백엔드까지 바로 붙이기
- 왜 대안을 버렸는지: 초기 게이트를 넓히면 구현/검증 비용이 급격히 커지고 Playwright 재현성이 떨어진다.

- 결정: Playwright는 real mic/audio 대신 fake media + injected mock voice APIs로 닫는다.
- 이유: CI에서 결정론적이며 브라우저 정책 차이로 인한 flake를 줄일 수 있다.
- 대안: 실제 마이크 입력과 브라우저 음성 API를 직접 사용
- 왜 대안을 버렸는지: CI/헤드리스 환경에서 안정성이 낮고 디버깅 비용이 높다.

- 결정: CI는 `check` / `e2e` 2-job 구조로 분리한다.
- 이유: build/type/unit 실패와 browser E2E 실패를 분리해 원인을 빨리 드러낼 수 있다.
- 대안: 기존 단일 job 유지
- 왜 대안을 버렸는지: voice demo E2E가 추가된 현재 구조에서는 Playwright 의존 구간이 quality gate와 섞이는 비용이 더 커졌다.

- 결정: Figma tool이 없는 세션에서는 구현 상태 screenshot + handoff 문서로 parity를 준비한다.
- 이유: 세션 의존성 때문에 실제 Figma 편집이 막혀도 설계 업무를 멈추지 않을 수 있다.
- 대안: Figma tool이 보일 때까지 대기
- 왜 대안을 버렸는지: 사용자의 개입을 최소화해야 하고, 다음 세션에서 바로 이어갈 수 있는 준비물이 더 중요했다.

## 6. 잘못 생각했던 점 / 수정된 이해
- 처음에 잘못 생각한 점: `speechSynthesis` 객체 자체를 mock object로 통째로 교체해도 Playwright에서 충분할 것이라고 봤다.
- 왜 그 생각이 틀렸는지: 일부 브라우저 컨텍스트에서는 real `speak()` 호출이 남아 `SpeechSynthesisUtterance` 타입 오류가 났다.
- 실제 원인: 객체 교체보다 메서드 패치가 더 안전한 브라우저 경계였다.
- 다음부터의 판단 기준: 브라우저 내장 객체는 가능하면 인스턴스 전체 교체보다 메서드 override를 우선 고려한다.

- 처음에 잘못 생각한 점: voice demo unit test는 `userEvent + fake timers` 조합으로 그대로 안정적으로 돌 것이라고 봤다.
- 왜 그 생각이 틀렸는지: timer 제어와 userEvent가 맞물리며 5초 timeout으로 멈췄다.
- 실제 원인: 상호작용 복잡도에 비해 event loop 제어가 과했다.
- 다음부터의 판단 기준: timer-driven state machine unit test는 `fireEvent`로 단순화하고 timer만 명시적으로 제어한다.

- 처음에 잘못 생각한 점: Figma tool이 보이지 않으면 그 라운드는 바로 멈추는 편이 맞다고 볼 수 있었다.
- 왜 그 생각이 틀렸는지: 구현 상태 screenshot과 parity 문서만으로도 다음 세션을 크게 앞당길 수 있었다.
- 실제 원인: 설계 결과물의 매체를 Figma tool 하나로만 한정해서 봤다.
- 다음부터의 판단 기준: Figma 직접 편집이 막혀도 state capture + handoff docs를 먼저 만들어 다음 세션 비용을 줄인다.

### 이슈 3
- 증상: 상태 screenshot 캡처 스크립트가 첫 시도에 실패했다.
- 오류 메시지: `ERR_MODULE_NOT_FOUND`, `ERR_CONNECTION_REFUSED`
- 영향 범위: Figma parity reference 생성 지연
- 처음 의심한 원인: Playwright 패키지 자체 문제
- 실제 원인: 임시 스크립트 경로와 로컬 dev server 부재

- Agent C는 voice demo 하네스와 E2E gate를 먼저 고정하게 만들었고, 최종 verdict는 `SHIP`이었다.

## 15. 사람이 나중에 봤을 때 유용한 한 문단 회고
오늘은 홈페이지가 “보이는 상태”에서 “실제로 체험 가능한 상태”로 넘어간 날이었다. 홈의 정적 데모 블록을 브라우저 네이티브 음성 데모로 교체하면서, 테스트 가능한 상태 machine과 deterministic E2E 경로를 함께 설계했다. 그 결과 구현과 검증이 한 번에 묶였고, CI도 그 구조에 맞게 다시 정리됐다. Figma 도구가 없는 세션이라는 제약은 남았지만, 상태 screenshot과 handoff 문서를 남겨 다음 세션의 설계 반영 비용을 크게 줄였다.
